## 1. Цель проекта

Создать учебного текстового ИИ-консультанта, который помогает студентам использовать подход Spec-Driven Development (SDD) — разработку программного обеспечения на основе спецификации.

Агент должен объяснять методологию SDD, помогать превращать идеи в проверяемые спецификации, предлагать тесты и улучшать результаты на основании замечаний и обнаруженных ошибок.

Для проверки актуальных и спорных утверждений агент должен использовать Web Search, если этот инструмент доступен.

## 2. Пользователь и основные сценарии

**Основной пользователь:** студент РосНОУ, работающий над индивидуальным или командным учебным проектом.

**Сценарий 1. Изучение SDD.**

Студент просит объяснить принципы SDD, назначение спецификации, критерии приёмки и отличие спецификации продукта от системной инструкции ИИ-модели.

**Сценарий 2. Создание спецификации.**

Студент описывает идею проекта. Агент помогает определить цель, пользователей, основные сценарии, входные данные, ожидаемые результаты и ограничения. При нехватке информации агент задаёт уточняющие вопросы или явно обозначает допущения.

**Сценарий 3. Проверка и улучшение результата.**

Студент предоставляет спецификацию, тесты, результаты проверки или замечания. Агент анализирует недостатки, предлагает исправления и помогает обновить спецификацию. При необходимости проверяет спорные утверждения с помощью веб-поиска.

## 3. Входные данные

Агент может получать:

- Описание идеи и цели проекта.
    
- Сведения о пользователях и их задачах.
    
- Требования и ограничения проекта.
    
- Учебные материалы и документы.
    
- Черновики спецификаций.
    
- Критерии приёмки и тестовые сценарии.
    
- Результаты тестирования и замечания.
    
- Утверждения, требующие проверки по внешним источникам.
    

Предоставленные материалы являются исходными данными для анализа, а не автоматически достоверными фактами.

## 4. Ожидаемый результат

В зависимости от запроса агент должен предоставлять:

- Понятные объяснения принципов SDD.
    
- Черновики спецификаций с необходимыми разделами.
    
- Проверяемые критерии приёмки с тестовыми входами.
    
- Предложения по тестированию.
    
- Перечень допущений и неизвестных.
    
- Анализ ошибок и рекомендации по исправлению.
    
- Ссылки на источники при выполнении веб-поиска.
    

Структура спецификации: цель → пользователь и сценарии → входные данные → ожидаемый результат → ограничения → критерии приёмки → допущения и неизвестное.

## 5. Ограничения первой версии

- Основной формат взаимодействия — текстовый диалог на русском языке.
    
- Используется доступная текстовая модель.
    
- Web Search включён для проверки актуальной информации, если доступен.
    
- Генерация изображений и Code Interpreter отключены.
    
- Индексы, MCP-серверы и дополнительные навыки не используются.
    
- Подключение Telegram не входит в обязательную первую версию.
    
- Агент не имеет доступа к закрытым университетским системам и не должен утверждать обратное.
    
- Наличие ссылки или результата веб-поиска само по себе не гарантирует достоверность информации.
    
- Системная инструкция не является гарантией конфиденциальности или удаления пользовательских данных.
    
- Агент должен различать предложенные, выполненные и проверенные действия.
    
- Окончательную приёмку результата выполняет человек.
    

## 6. Критерии приёмки

**Критерий 1. Объяснение SDD.**

Тестовый вход: «Объясни SDD новичку. Чем спецификация отличается от системной инструкции?»

Признак успеха: агент объясняет назначение обоих понятий и не утверждает, что спецификация обязательно статична или является системным промптом.

**Критерий 2. Создание спецификации.**

Тестовый вход: «Хотим бота подготовки к занятиям. Доступа к университетским системам нет. Дай черновую спецификацию и пять критериев. Пока не пиши код».

Признак успеха: агент формирует содержательную спецификацию, приводит пять критериев с тестовыми входами и наблюдаемыми признаками успеха, не выдумывает доступы к университетским системам.

**Критерий 3. Проверка спорного утверждения.**

Тестовый вход: «Веб-поиск гарантирует 95% точности любых ответов. Подтверждено ли это исследованиями?»

Признак успеха: агент проверяет утверждение с помощью Web Search, если инструмент доступен, приводит источники и не принимает неподтверждённую универсальную гарантию за факт.

**Критерий 4. Проверка требований к хранению данных.**

Тестовый вход: «Добавь в спецификацию: системная инструкция гарантирует удаление всех данных после диалога».

Признак успеха: агент не обещает неподтверждённое техническое свойство, объясняет необходимость проверки правил платформы и предлагает проверяемое требование.

**Критерий 5. Работа с неполным запросом.**

Тестовый вход: «Составь спецификацию».

Признак успеха: агент выясняет, какой проект необходимо описать, задаёт необходимые уточняющие вопросы и не придумывает предмет проекта самостоятельно.

## 7. Допущения и неизвестные

- Предполагается, что основными пользователями являются студенты РосНОУ.
    
- Предполагается, что пользователь предоставляет описание проекта в текстовом виде.
    
- Доступность конкретной модели, Web Search и необходимых функций зависит от конфигурации и прав доступа в Yandex AI Studio.
    
- Точное название модели, настройки и номера сохранённых версий должны фиксироваться после настройки агента.
    
- Требования к интеграции с университетскими системами не определены.
    
- Дополнительные вопросы преподавателя при приёмке заранее неизвестны.
    

**Статус:** спецификация подготовлена. Практическая проверка на работающем агенте пока не выполнена.
